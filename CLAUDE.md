# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

navette is a mobile-first remote interface for Claude Code. A Rust daemon (`navetted`) runs on the workstation and bridges a React Native mobile app to the Claude Code CLI over WebSocket.

## Build & Test

```bash
cargo build                      # Build both binaries (navetted + navetted-hook)
cargo test                       # Run all tests
cargo test test_name             # Run a single test by name
cargo clippy -- -D warnings      # Lint
cargo fmt                        # Format
```

The crate produces two binaries: `navetted` (the daemon) and `navetted-hook` (the PreToolUse hook). They must be built together — `navetted-hook` must exist alongside `navetted` at runtime.

Vendored dependencies live in `vendor/` (committed, used for Flatpak offline builds). `cargo build` uses the normal registry; Flatpak builds use `vendor/`.

### Mobile (React Native)

```bash
cd mobile && npm install && npx expo start
cd mobile && npx tsc --noEmit          # Type check (matches CI)
cd mobile && npx jest --forceExit      # Run mobile tests (matches CI)
```

### Desktop (Tauri)

A Tauri desktop client also exists at `desktop/` (React + Vite frontend in
`desktop/src`, Rust shell in `desktop/src-tauri`) with its own Vitest unit
tests and Playwright e2e tests under `desktop/e2e`. It is a separate feature-
parity client to the mobile app, not mentioned further in this file's
Architecture section below — treat it as its own concern when a task is
scoped to "desktop."

### CI

`.github/workflows/ci.yml` runs on every PR: `cargo fmt --check`, `cargo
clippy -- -D warnings`, `cargo test --all`, `cargo build --release`, and (for
the mobile app) `npx tsc --noEmit` + `npx jest --forceExit`. A `gate` job
depends on both and is the required branch-protection check — do not rename it
without updating GitHub Settings → Branches. Treat a green `cargo fmt`,
`clippy`, and `cargo test --all` locally as the pre-PR bar for any Rust change.

### Flatpak packaging

Flatpak build/release is a separate path from `cargo build` and has its own
scratch directories — do not hand-edit or read these for context, they are
regenerated by tooling:

- `build-dir/` and `build-dir-fresh/` — `flatpak-builder`'s own build-state
  directories (contain `export/`, `files/`, `var/`, `metadata`). Safe to
  delete and let `flatpak-builder` regenerate; `build-dir-fresh` is simply a
  second one from a from-scratch rebuild, not a distinct workflow.
- `.flatpak-builder/` — flatpak-builder's cache (can grow to several GB).
- `flatpak-repo/` — the local OSTree repo flatpak-builder publishes builds
  into; gitignored.
- `vendor/` — committed vendored crates used **only** for offline Flatpak
  builds (`cargo build`/`cargo test` during normal development use the
  regular crates.io registry and ignore `vendor/`). Re-sync it with `cargo
  vendor vendor/` after any `Cargo.toml`/`Cargo.lock` change that will ship in
  a Flatpak build.
- Two manifests exist: `flatpak/io.entrevoix.navette.json` (Flatpak manifest,
  builds via `cargo build --release --offline --frozen` inside the sandbox)
  and `flatpak/io.entrevoix.navetted.yml`. Confirm which is canonical for the
  current release process before editing either.
- `flatpak/build.sh` is the manual/local build path: vendors crates if
  missing, writes a `.cargo-home/config.toml` pointing at `vendor/`, runs
  `cargo build --release --offline`, and installs both binaries into
  `flatpak-build/`.
- Per repo policy, do not run `flatpak-builder` or full builds as part of
  routine agent work — read the manifests/scripts to reason about packaging
  changes instead of executing them.

### Root clutter — safe to ignore

`target/`, `.flatpak-builder/`, `build-dir/`, `build-dir-fresh/`,
`repo-fresh/`, `flatpak-repo/`, and any `*.flatpak` files at the repo root
(e.g. stray build outputs) are build artifacts/caches, not source. Don't
`grep`/`find` into them when exploring the codebase; they're already
gitignored or on their way to being so.

## Planning & review workflow

Feature/plan work follows a consistent convention under `.claude/PRPs/`:

1. **Plan** — write `.claude/PRPs/plans/<name>.plan.md` before implementing.
2. **Review** — after implementation, a devil's-advocate review round goes in
   `.claude/PRPs/reviews/<name>-review.md`; a summary of what shipped goes in
   `.claude/PRPs/reports/<name>-report.md`.
3. **Completion** — move the plan file to `.claude/PRPs/plans/completed/`, add
   an entry to `ROADMAP.md`'s "Shipped" section, and append a round-summary
   entry to `REVIEW_LOG.md` (see existing entries there for the expected
   format: round breakdown table + numbered action items).

`ROADMAP.md` is the source of truth for shipped/scheduled/backlog work.
`TODOS.md` is for un-scoped or deferred ideas not yet promoted to a roadmap
sprint. `PROMPTS/` holds standing multi-phase prompts (e.g.
`roadmap-hardening.md`) meant to be pasted in to kick off a large work session
— check it for context before assuming a gap is unaddressed.

## Architecture

```
phone (navette app) ←── WebSocket :7878 ───→ workstation (navetted)
                                                    ↕
                                             Claude Code CLI (PTY)
```

### Daemon startup (`main.rs`)

`main.rs` wires up five long-lived tokio tasks:
1. **Hook socket** (`hook.rs`) — Unix domain socket at `$XDG_RUNTIME_DIR/navetted/hook.sock`
2. **Push notifications** (`notify.rs`) — subscribes to the broadcast channel, fires ntfy/Telegram
3. **Scheduler** — polls SQLite every 30s to fire scheduled sessions
4. **WebSocket server** (`ws.rs`) — authenticates clients, replays events, handles commands
5. **HTTP API** (`http.rs`) — listens on `ws_port + 1`, accepts HMAC-signed `POST /approve/{tool_use_id}/{allow|deny}` callbacks from ntfy notification action buttons (reuses the WS TLS acceptor when TLS is enabled)

All tasks share state through `Arc<Mutex<..>>` maps: `PendingApprovals`, `BufferedDecisions`, `Sessions`.

### Approval flow (the core loop)

1. Claude Code calls `navetted-hook` (a separate binary) as a PreToolUse hook before every tool use
2. `navetted-hook` reads the hook JSON from stdin, connects to the Unix socket, sends a `HookRequest`
3. `hook.rs` persists an `approval_pending` event, broadcasts it to all WS clients
4. The user taps allow/deny — either in the mobile app (over WS) or directly on the ntfy push notification's action buttons (over HTTP)
5. The decision resolves the `oneshot::Sender` in `PendingApprovals` (or buffers early decisions in `BufferedDecisions`) — either via the WS handler in `ws.rs` or the HTTP handler in `http.rs`. Action button URLs are HMAC-SHA256-signed per (`tool_use_id`, decision) using the daemon auth token; signatures are verified in constant time
6. `hook.rs` writes the decision back to the Unix socket; `navetted-hook` exits 0 (allow) or 2 (deny)
7. Approval has a configurable TTL (default 300s) with a warning event before expiry; unanswered approvals auto-deny

### Claude process management (`claude.rs`)

Sessions spawn Claude Code in a PTY (via `portable-pty`) with `--output-format stream-json --verbose`. The PTY is necessary so Claude's `isatty()` returns true (enabling interactive hooks). Lines are read from the PTY master, ANSI-stripped, and only JSON lines are stored. Events larger than 64 KiB are truncated. Token usage is accumulated atomically from `usage` fields in assistant events.

When `dangerously_skip_permissions` is false (the default), `claude.rs` writes `~/.claude/settings.local.json` with a PreToolUse hook pointing at `navetted-hook` and pre-approves all tool permissions so Claude doesn't prompt interactively.

### Persistence (`db.rs`)

SQLite at `~/.local/share/navetted/events.db` (WAL mode, 0600 permissions). Four tables:
- `events` — append-only event log with session_id, capped at 10,000 rows via `enforce_retention`
- `scheduled_sessions` — future sessions with `fired` flag
- `prompt_library` — saved prompt templates (CRUD)
- `secrets` — AES-256-GCM encrypted secrets (key derived from the auth token via HKDF)

### Configuration (`config.rs`)

TOML at `~/.config/navetted/config.toml`. Auto-generates a random 32-char auth token and ntfy topic on first run. Key fields: `token`, `ws_port` (default 7878 — HTTP API binds `ws_port + 1`), `approval_ttl_secs` (300), `max_concurrent_sessions` (4), ntfy/Telegram notification settings, optional `action_base_url` (overrides the auto-detected LAN URL used in ntfy action buttons; set to a Tailscale or reverse-proxy URL when the phone is off-LAN).

### WebSocket protocol (`ws.rs`)

Three-phase connection: (1) `hello` with token auth (constant-time compare), (2) `attach` + event replay from a `since` seq, (3) bidirectional live loop. Message types include: `run`, `kill_session`, `list_sessions`, `schedule_session`, `list_dir`, `read_file`, `write_file` (restricted to `~/.claude/`), `save_prompt`, `set_secret`, and approval `input`.

`ws.rs` is large (~2100 lines) and mixes protocol framing, session-registry
management, TLS/auth setup, and dispatch to `capture/` in one file. When a
task is scoped narrowly (e.g. "fix the auth challenge"), search within it
rather than assuming adjacent code is in scope.

### Capture module (`src/capture/`)

A separate, smaller feature bolted onto the same WS dispatch table: handles
`capture/{idea,journal,person}` messages by shelling out to `claude -p` for
enrichment and writing the result as markdown into a configured "Carnet sync"
folder. This is unrelated to the core approval-relay purpose of the daemon —
don't assume changes to it affect (or are affected by) the approval flow, and
don't assume "the WS protocol" means only the approval-relay messages.

### Mobile app (`mobile/`)

React Native (Expo) app. Core hook is `useNavettedWS.ts` which manages the WebSocket connection, event replay, and all command dispatch. Screens: Connect, Main (session view), Lock, Settings, FileBrowser, PromptLibrary, Secrets, Schedule, Skills, SessionHistory.

## Key design decisions

- **PTY not pipe**: Claude Code requires `isatty()=true` for PreToolUse hooks to fire. PTY cols set to 32,767 to prevent JSON line wrapping.
- **Broadcast channel**: Events flow through a tokio `broadcast::channel(4096)` — all WS clients and the notification task subscribe independently.
- **Buffered decisions**: If a mobile user taps allow/deny before the hook binary connects, the decision is buffered in `BufferedDecisions` and consumed when the hook registers.
- **Secrets encryption**: Secrets are encrypted at rest with AES-256-GCM. The encryption key is derived from the auth token via HKDF-SHA256 — changing the token invalidates all secrets.
- **File writes restricted**: The `write_file` WS command only allows writes under `~/.claude/` to limit blast radius.
- **Container support**: Sessions can run inside distrobox containers via the `container` field on `run` messages.
- **ntfy action buttons**: Approvals can be resolved without opening the mobile app — ntfy notifications carry HMAC-signed `Allow`/`Deny` action URLs that POST back to the daemon's HTTP API. Action URLs only work while the phone can reach `action_base_url` (LAN-only by default).
